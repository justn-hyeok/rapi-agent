# 제품 요구사항

## 1. 제품 정의

라피는 개인이 신뢰하는 정보원과 개발 프로젝트의 변화를 지속적으로 관찰하고,
중복과 소음을 줄인 뒤 Discord, 이메일, MDX 블로그로 전달하는 개인용 정보·실행
에이전트다.

라피의 핵심 가치는 단순 수집량이 아니라 다음 세 가지다.

- 무엇이 새로 생겼고 왜 중요한지 설명한다.
- 사용자가 원하는 시점과 채널로 다시 찾을 수 있게 전달한다.
- 개발 요청을 실행 가능한 명세로 바꿔 OMP에 안전하게 넘긴다.

## 2. 사용자와 인터페이스

초기 사용자는 시스템 소유자 한 명이다. Discord DM 또는 허용된 개인 서버
채널이 기본 인터페이스다.

주요 상호작용은 다음과 같다.

- “오늘 중요한 것만 보여줘”처럼 브리핑을 요청한다.
- 저장소, 조직, 키워드, 카테고리, 발송 주기를 구독하거나 해제한다.
- 특정 원문의 출처와 수집 시각을 확인한다.
- 분류 오류, 중복, 불필요한 출처에 피드백을 준다.
- 개발 요청을 설명하고 라피가 만든 작업 명세를 검토하거나 승인한다.
- 실패한 수집·발송·작업 실행의 상태와 재시도 결과를 확인한다.

## 3. 기능 범위

### 3.1 정보 수집

- 일반 웹훅 수신
- 지정 GitHub 저장소와 조직의 커밋, PR, 이슈 변화 수집
- RSS/Atom, 뉴스, 커뮤니티, 일반 사이트 수집
- API가 없거나 로그인된 브라우저 상태가 필요한 공개·개인 정보의 Aside 기반
  리서치
- 출처별 폴링 주기, 커서, ETag/수정 시각, 실패 횟수 관리
- 원문, 출처 URL, 작성·수집 시각, 작성자, 라이선스/공개 범위 메타데이터 보존

Aside 리서치는 무제한 크롤러가 아니다. 사용자가 지정한 출처와 목적에 한정하며,
사이트 정책과 접근 권한을 지킨다.

### 3.2 처리

- 출처별 payload를 공통 `SourceItem` 형식으로 정규화
- 외부 ID, canonical URL, 내용 fingerprint를 이용한 단계적 중복 제거
- 규칙과 모델을 조합한 카테고리·키워드 분류
- 개별 항목 요약과 여러 항목을 묶은 브리핑 생성
- 원문과 요약의 연결 및 처리 버전 기록
- 사용자 피드백을 규칙과 구독 설정에 반영

요약이 실패하거나 신뢰도가 낮아도 원본은 유실하지 않는다. 사실과 해석을
구분하고, 발송물에는 원문으로 이동할 수 있는 링크를 유지한다.

### 3.3 구독과 발송

구독 조건은 다음 요소를 조합한다.

- 출처 또는 GitHub 저장소·조직
- 카테고리와 포함/제외 키워드
- 즉시, 일간, 주간 등의 발송 주기
- Discord DM, Discord 채널, 이메일
- 조용한 시간대와 최대 항목 수

Rapi Newsletter는 발송 전 포함 항목을 고정한 `DeliveryBatch`를 만들고, 채널별
발송 결과를 기록한다. 재시도 시 이미 성공한 대상을 다시 보내지 않는다.

### 3.4 Discord

- 공식 봇 계정과 Discord API만 사용
- 허용 사용자·서버·채널 목록 적용
- 슬래시 명령과 자연어 대화 지원
- 긴 결과의 페이지 분할 또는 블로그 링크 전환
- 승인 요청에는 대상, 영향, 예상 변경, 만료 시각을 표시
- 관리자 명령과 일반 조회 명령의 권한 분리

초기 명령 후보:

| 명령 | 목적 |
| --- | --- |
| `/brief [today|week]` | 현재 브리핑 조회 |
| `/search <query>` | 보관 항목 검색 |
| `/subscribe` | 구독 생성·수정 |
| `/unsubscribe` | 구독 해제 |
| `/sources` | 수집원과 상태 조회 |
| `/deliveries` | 최근 발송과 실패 확인 |
| `/task` | 개발 요청을 작업 명세로 변환 |
| `/approve <id>` | 대기 중인 외부 실행 승인 |
| `/cancel <id>` | 대기 중인 실행 취소 |

### 3.5 이메일

- 전용 메일 계정의 SMTP 또는 제공 API 사용
- 텍스트와 HTML을 함께 제공
- 발송 대상, Message-ID, 공급자 응답, 성공·실패 상태 기록
- 반송과 일시 실패를 구분해 제한적으로 재시도
- 테스트 수신자와 실제 수신자 분리
- 수신 해제 또는 해당 구독 중지 경로 제공

### 3.6 MDX 블로그

블로그는 Notion을 대체하는 읽기·보관·공개 계층이다.

- 일일·주간 브리핑
- 분류별 수집함과 GitHub 변화 기록
- 공개 가능한 분석글, 개발 로그, 기능 업데이트
- 뉴스레터 웹 버전과 샘플
- frontmatter 기반 공개 범위(`private`, `unlisted`, `public`) 관리
- 생성물에 출처, 생성 시각, 수정 이력 표시

비공개 항목은 정적 빌드 산출물에 포함하지 않는다. 공개 전 개인 데이터, 비공개
저장소 내용, 라이선스 제한 원문이 섞이지 않았는지 검사한다.

### 3.7 개발 작업 연결

라피는 코드를 직접 수정하지 않는다. 개발 요청을 아래 정보를 가진 작업 명세로
고정한 뒤 OMP 실행 계층에 전달한다.

- 작업 ID, 요청자, 생성 시각
- 목표와 비목표
- 대상 저장소, 기준 브랜치·리비전, 작업공간
- 요구사항과 완료 조건
- 제약, 권한, 위험 수준, 승인 참조
- 필요한 테스트와 산출물
- 실행 상태, 결과 보고서, 커밋·PR 링크

코드 변경, 커밋, push, PR, 배포처럼 외부 상태를 바꾸는 권한은 작업 명세에
명시적으로 포함돼야 한다. 승인되지 않은 권한은 OMP에 위임하지 않는다.

## 4. 비기능 요구사항

### 신뢰성

- 프로세스 재시작 뒤에도 수집 커서와 작업 상태 복구
- 동일 이벤트의 중복 수신과 재시도에 안전
- 실패는 무한 재시도하지 않고 dead-letter 상태로 격리
- DB 백업과 복구 연습 절차 보유

### 관찰 가능성

- 수집원별 마지막 성공, 지연, 오류 횟수
- 큐 적체, 처리 시간, 모델 비용, 발송 성공률
- 작업 ID를 통한 수집→요약→발송/실행 추적
- Discord에서 핵심 상태 조회 가능

### 보안과 개인정보

- 최소 권한 토큰과 별도 서비스 계정 사용
- 비밀값 로그 마스킹 및 저장소 커밋 방지
- Discord 사용자 ID 기반 권한 검사
- 공개 블로그 배포 전 민감정보 검사
- 원본 보존 기간과 삭제 요청을 정책으로 관리

### 비용 통제

- 출처별 폴링 상한과 모델 호출 예산
- 동일 콘텐츠 요약 결과 캐시
- 일/월 비용 한도 초과 시 저비용 모드 또는 처리 보류
- 비용 증가 작업은 Discord에 근거를 표시하고 승인 요청

## 5. MVP 완료 조건

MVP는 다음 시나리오가 VM 재시작을 포함해 종단 간 통과할 때 완료다.

1. GitHub와 RSS 출처에서 새 항목을 수집해 원본과 정규화 결과를 저장한다.
2. 중복 이벤트를 다시 주입해도 사용자에게 한 번만 전달된다.
3. Discord에서 구독을 만들고 일간 브리핑을 DM으로 받는다.
4. 같은 브리핑을 테스트 이메일로 받아 링크와 텍스트가 정상 표시된다.
5. 공개 가능한 브리핑이 MDX로 생성되고 블로그 빌드에서 확인된다.
6. Discord의 개발 요청이 작업 명세가 되고, 승인 후 OMP로 전달돼 결과 상태가
   다시 Discord에 기록된다.
7. 수집기 또는 발송기를 강제 재시작해도 누락이나 중복 발송 없이 복구된다.
8. 잘못된 사용자, 서버, 채널의 명령과 승인이 거부된다.

## 6. 초기 범위에서 제외

- Discord 개인 계정 자동화와 self-bot
- 불특정 사이트에 대한 대규모 크롤링
- 다중 사용자 SaaS와 결제
- 라피 프로세스가 직접 수행하는 코드 수정
- 승인 없이 이루어지는 배포, 결제, 계정 설정 변경
- 완전 자동 공개 게시
