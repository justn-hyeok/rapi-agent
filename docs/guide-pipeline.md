# 출처가 붙은 입문 가이드 파이프라인 (기획)

사용자가 "Cursor 처음 쓰는 법"처럼 물으면, 라피가 아카이브에서 근거를 찾아 출처
링크가 붙은 입문 가이드를 만든다. 이 문서는 범위와 단계를 정한다. 소유자는
포트폴리오용으로 n8n·LangChain·LangGraph를 쓰길 원했고, 그래프 RAG를 바로 붙일 수
있는 준비와 RAG를 요청했다. 모든 새 기능은 플래그를 끈 채 배포한다.

## 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 검색 계층(`Retriever`), 질의 확장+LLM 재순위, 그래프 스키마·`GraphStore` | 구현됨(플래그 모두 꺼짐) |
| 2 | LangChain 부품(`RapiRetriever`, 계획 체인)으로 근거 검색 | 구현됨(`BLOG_GUIDE_GRAPH_ENABLED`) |
| 3 | LangGraph 상태 그래프: 계획 → 검색 → 초안 → 출처 검증(1회 재시도) → 소유자 승인 | 구현됨(같은 플래그) |
| 4 | n8n: 게시 이벤트를 받아 알림 등 외부 연결(내부 접속만, 별도 알림 후 배포) | 예정 |
| 5 | 챗봇·웹 포털 진입점, 중복 정리, 문서 갱신 | 예정 |

## 검색 설계 (1단계)

임베딩 모델이 없다. 현재 모델 API(Anthropic)에는 임베딩 엔드포인트가 없고, 새 키와
지출 없이 시작하기로 했다. 대신 아카이브가 작다는 점을 이용한다.

1. **질의 확장**: 싼 모델이 질문을 키워드·동의어로 넓힌다.
2. **후보 수집**: 기존 키워드 검색(`tsvector`)을 원 질문과 확장 질의로 각각 돌려 합친다.
3. **재순위**: 모델이 후보마다 관련도(0~3)를 매긴다. 0은 버린다.
4. **융합**: 키워드 순위와 모델 순위를 RRF로 합친다.
5. 모델이 실패하거나 예산이 소진되면 키워드 결과로 되돌아간다(답변을 막지 않는다).

`Retriever` 인터페이스 뒤에 두므로, 나중에 임베딩 키가 생기면 `VectorRetriever`를
같은 자리에 꽂는다. 평가셋으로 키워드만 쓸 때와 재순위를 비교해 임베딩이 필요한지
숫자로 판단한다.

## 그래프 RAG 준비

그래프 DB 서버는 띄우지 않는다. Postgres 테이블로 시작하고 `GraphStore` 인터페이스
뒤에 둔다.

- `graph_entities`: 도구·회사·개념·레포 등 엔티티. 별칭 포함.
- `graph_edges`: `source → relation → target`, 근거 문서 키. 순회는 재귀 CTE.
- 엔티티·관계 추출은 문서 인덱싱 때 모델로 한다. 플래그를 끄고, 배치 크기와 비용을
  제한하며, 켜기 전에 문서 수와 예상 비용을 소유자에게 보인다.
- `GraphRetriever`는 질문 속 엔티티에서 이웃 문서를 확장한다.
- 나중에 Neo4j 등으로 옮길 때는 `GraphStore` 구현만 바꾼다.

## 지켜야 할 것

- 새 플래그는 꺼 둔 채 배포하고, 켜기는 소유자 결정이다.
- 공개 기능(`archive_qa` 등)의 모델 호출은 기존 월 상한(`$20`) 안에서 집계한다.
- 키·비밀값은 VM에서 소유자가 넣는다. 다른 도구에서 꺼내 옮기지 않는다.
- 새 마이그레이션은 운영 최대 번호 다음(0031)을 쓰고 반복 가능한 rollback을 둔다.

## 알려진 문제: 지금은 검색할 문서가 없다

2026-10-26 운영 확인: `archive_documents`가 0건이다. 아카이브는 라피가 **공개로
발행한 글**(학습자 호, 커뮤니티 게시, 블로그)만 담는다. 학습자 호는 한 번도 발송되지
않았고, 블로그 글은 DB에 0건이며, 게시된 커뮤니티 글 24건은 임베드에 `https` 링크가
없어 색인 조건에 맞지 않는다. 즉 이 단계의 코드는 준비됐지만 비춰 볼 말뭉치가 비어 있다.

## 결정: 수집한 공개 항목을 말뭉치에 넣는다 (2026-10-26)

"라피가 발행한 것만 답한다"는 규칙은 말뭉치를 비게 만들었다. 그래서 다음 범위로 넓힌다.
플래그 `ARCHIVE_SOURCES_ENABLED`(기본 꺼짐)가 켜져 있을 때만 적용한다.

- 대상: 공개 항목(`visibility=public`)이면서 활성·공개 수집원의 것, 최근 90일 안, `https` 링크,
  제목이 있고, 본문 만료(`retentionExpired`)가 아닌 것. 같은 내용(`content_fingerprint`)은 하나만.
- 최신 2000건까지만 유지한다(검색·그래프 추출 비용 상한).
- 아카이브에는 제목, 400자 요약, 원문 링크만 둔다. 본문 전체는 복사하지 않는다.
- 항목이 삭제되거나 비공개로 바뀌거나 본문이 만료되면 다음 동기화(5분 이내)에 아카이브에서
  빠지고, 그래프의 엔티티·관계도 함께 지워진다(`ON DELETE CASCADE`).
- 비공개·`aside` 출처는 계속 제외한다. 답변은 요약을 바탕으로 쓰고 원문 링크를 붙인다.

## 2·3단계 구현 결과: 근거를 찾아 쓰는 가이드 초안

`packages/agent/src/guide-graph.ts`의 `GuideComposer`가 소유자의 "블로그 초안: 주제" 요청을
처리한다. 이전에는 주제 한 줄만 모델에 넘겨서 근거가 없었다.

```
plan ─▶ retrieve ─▶ (근거 2개 이상?) ─▶ write ─▶ verify ─┬─▶ 끝(초안)
          │              │ 아니오                         └─▶ write(1회 재시도)
          └ RapiRetriever └▶ 끝("근거를 찾지 못했어요")
```

- **plan**: LangChain `RunnableSequence`로 주제를 검색어 3개 이하로 바꾼다. 실패하면 주제로만 검색한다.
- **retrieve**: LangChain `BaseRetriever`(`RapiRetriever`)가 `HybridRetriever`(키워드+재순위+그래프)를
  감싼다. 검색어별 결과를 링크로 합쳐 최대 8개를 근거로 쓴다.
- **write**: 기존 `BlogService.generate`(JSON 스키마, 자료에 있는 https 링크만 인용)를 그대로 쓴다.
  근거의 제목·요약·주소만 `<근거>`로 넘기고 `<`·`>`는 지워 태그 위조를 막는다.
- **verify**: 본문 "참고한 곳"에 서로 다른 https 링크가 2개 이상인지 본다. 아니면 한 번 다시 쓰고,
  그래도 부족하면 보류 사유를 소유자에게 알린다.
- 결과는 언제나 **초안**이다. 기존 버튼(게시/수정/버리기)과 소유자 승인은 그대로다.
