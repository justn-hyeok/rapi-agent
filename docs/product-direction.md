# 제품 방향 전환 (초안 2판, 2026-10-24)

이 문서는 라피의 제품 방향을 다시 정한 결과를 정리한다. 기존
[제품 요구사항](product-requirements.md)과 [로드맵](roadmap.md)은 "개인 Discord
중심 에이전트"를 전제로 작성됐다. 이 문서가 승인되면 두 문서와
[결정 기록](decisions.md)을 이 방향에 맞춰 고친다. 아직 코드 변경 지시는 아니다.

2판은 1판에 대한 독립 리뷰를 반영했다. 주요 변경은 다음과 같다.

- "이미 있는 것"을 코드 기준으로 다시 썼다.
- 0단계에 숫자로 된 성공·중단 조건을 넣었다.
- 근거가 없는 트랙과 기능은 보류로 내렸다.
- public-agent와 게이트웨이 원칙의 모순을 풀었다.

`(제안)` 표시는 사용자 확정이 필요한 기본안이다.

## 한 줄 정의

> 라피는 AI 도구를 쓰기 시작한 사람에게, 필요한 소식만 원하는 빈도로 보내 주는
> 큐레이터다. 그 위에 아카이브 Q&A와 작업 기능을 단계적으로 연다.

1판의 정의는 "콘텐츠·작업·AI 허브"였다. 범위가 넓어서 18개 명령을 기둥 이름으로
다시 묶는 데 그칠 위험이 있었다. 2판은 근거가 있는 독자(학습자)와 기능(큐레이션,
빈도 선택)을 앞에 둔다. 나머지 기둥은 조건이 충족될 때 연다.

## 왜 바꾸는가

- **축이 없다.** "justn 개인 비서"와 "공개 커뮤니티 봇"이 섞여 있다. 기능이
  사용자가 할 일이 아니라 구현 단위로 나뉘어 있다(slash 명령 18개, 자연어
  대화, 코드 실행 경로 2개).
- **사용자가 무엇을 써야 할지 모른다.** 아침에 무엇을 열어 무엇을 보면 되는지에
  대한 답이 없다.
- **구독자와 운영자가 쓸 웹이 없다.** 운영자 전용 서명 링크 브리핑 페이지는 있다.
  하지만 구독 관리, 아카이브, 운영 상태를 볼 웹은 없다.
- **모든 것을 Discord에서 하려 한다.** 설정·조회·관리까지 slash 명령에 들어가
  있다.

## 근거: 사용자 인터뷰

### 인터뷰 1 (학습자, 2026-10)

- **AI 사용 현황**
  - ChatGPT로 공부·질문·정보 탐색, Gemini로 이미지 생성, Codex로 코딩을 한다.
  - Codex는 인터뷰 전날 VS Code 연동을 계기로 처음 써 봤다.
  - 유료 구독은 없다. Claude는 비용 때문에 쓰지 않는다. 돈이 생기면 유료 도구를
    살 생각은 있다.
- **가장 강한 반응**: 기간 한정 무료 AI 도구·프로모션 정리를 보내 준다는 제안
  ("네!!!!!!!!!!!", "완전 많아요").
- **채널**
  - Discord는 수시로 확인하고, 개인 DM으로 오면 볼 의향이 있다.
  - 메일은 오면 보지만 수시로 들어가지는 않는다.
  - 카카오톡은 홍보 메시지가 약 400개 쌓여 있어 잘 보는 채널이 아니다.
- **이용 조건은 알림 빈도다.**
  - "약간 진짜 너무 많이오면 안볼거같은데"
  - 빈도를 직접 정할 수 있다고 하자 "그럼 진짜 할거같은데"

### 해석

- 학습자는 AI를 이미 쓰고 있지만, 비용과 도구 경험에 제약이 있다.
- 많이 모아 주는 것보다 필요한 것만, 감당할 수 있는 빈도로 보내는 것이 이용
  조건이다.
- 이 독자층에게는 메일보다 Discord DM이 더 나은 발송 경로일 수 있다.

### 한계

- 1명이다.
- 무료 도구에 대한 반응은 제안을 먼저 듣고 나왔다. 실제보다 강하게 나왔을 수
  있다.
- "볼 것 같다"는 말이 실제 행동과 같지는 않다.
- 묻지 않은 것: 돈을 낼 의향, 적당한 빈도, "쓸 만하다"의 기준.

### 보류한 것

- **Instagram**: 인터뷰에서 가장 자주 볼 채널로 먼저 나왔다. 이번 계획에서는
  다루지 않는다.
- **개발 환경 커스터마이징**: 관심은 있었으나 "쉬워야 한다"는 조건이 붙었고,
  수요는 확인되지 않았다. 이번 계획에서는 다루지 않는다.

## 기둥과 여는 조건

네 기둥은 유지한다. 대신 기둥마다 **언제 여는지**를 정해, 한꺼번에 짓지 않는다.

| 기둥 | 지금 하는 것 | 여는 조건 |
|---|---|---|
| A. 콘텐츠 | 학습자 트랙 하나 | 0단계 성공 |
| D. 웹 | 구독 설정과 아카이브 최소판 | 0단계 성공 |
| B. 작업 | OMP 제거, 소유자 실행 엔진 정리 | 지금 가능(독자와 무관) |
| C. 게이트웨이 | 라피 내부 호출의 비용 집계 | 지금 가능. 외부 키 발급은 보류 |

### A. 콘텐츠: 학습자 트랙 + 블로그 아카이브

- **학습자 트랙**의 구성:
  - 무료 AI 도구·프로모션 정리. 기존 `free-tokens` 피드를 다시 쓴다.
  - 도구 입문 가이드. "Codex 처음 쓰기"처럼 막 써 보기 시작한 사람을 위한 글이다.
  - 개념 설명 위주로 다시 쓴 소식
- 구독자가 **빈도**를 직접 고른다. 빈도 설정은 부가 기능이 아니라 이용 조건이다.
  기존 `/구독` 주기 옵션을 구독자별 설정으로 확장한다.
- 블로그는 각 호의 웹 버전이자 아카이브다. 테스트에서만 호출되던 `MdxPublisher`를
  실제 게시에 연결한다.
- **기존 섹션·피드와 트랙의 관계**

  | 기존 | 학습자 트랙에서 |
  |---|---|
  | 큐레이션 `free-tokens` | 핵심 섹션 |
  | 큐레이션 `setup`, `stars` | 도구 입문 가이드의 재료 |
  | 큐레이션 `ai-blogs`, `projects` | 개념 설명 소식의 후보 |
  | 브리핑 섹션 `tools`(도구 변화) | 개념 설명 소식의 후보 |
  | 브리핑 섹션 `industry`, `github`, `korea` | 운영자 브리핑에만 남긴다. |

- **콘텐츠 규칙**: 요약과 원문 링크를 함께 둔다(PRD §3.2). 원문 전문을
  재배포하지 않는다. 재작성은 요약 범위 안에서 한다.
- **초기 품질 게이트** `(제안)`: 공개 발송 전에 운영자가 각 호를 승인한다. 오류
  없이 발송된 호가 쌓이면 자동 발송으로 바꾼다.

### B. 작업: 실행 엔진 하나

- **OMP 의존성을 뺀다.** 실행 경로는 ChatOps(`apps/chat`의 Codex 직접 실행)
  하나만 남기고, 입구와 분리된 실행 엔진으로 정리한다.
- **OMP 제거 범위**
  - 서비스: `apps/omp`, `ops/systemd/rapi-omp.service`, VM 유닛 중지·비활성화
  - bot: `OmpHttpAdapter` 사용, `/omp/callback`, `/작업`·`/승인` 정의
    (`apps/bot/src/run.ts`, `discord-http.ts`)
  - worker: `OmpHttpAdapter` 생성(`workers/runtime/src/run.ts:15,67-69`)
  - agent: `receiveOmpCallback` 등(`packages/agent/src/rapi-agent.ts`)
  - adapters: `packages/adapters/src/execution.ts`
  - monitor: omp health 항목(`apps/monitor/src/run.ts:280`)
  - 설정: `OMP_ENDPOINT`, `OMP_CALLBACK_SECRET`, `OMP_READY_URL`
    (`packages/config/src/index.ts:59-60,118`), `.env.example`
  - 배포·운영: `scripts/switch-release.mjs:56`, `ops/Caddyfile.example`,
    `docs/operations.md`의 OMP 공급자 설정
  - 테스트: `tests/providers.test.ts`, `tests/public-gateway.test.ts`,
    `tests/release-units.test.ts`, `tests/e2e/mvp.test.ts`
  - **MVP 매니페스트**: `tests/manifests/mvp.yaml`의 `approved_omp_execution_and_callback`
    조건을 ChatOps 실행 기록 조건으로 대체한다.
  - 기존 OMP 작업 기록은 DB에서 지우지 않고 보관 정책을 따른다.
- OMP에만 있던 Cursor·Command Code 실행은 다시 넣지 않는다 `(제안)`. 다른 공급자가
  필요해지면 게이트웨이의 모델 선택으로 해결한다.
- **GitHub App**: 처음에는 운영자 본인 레포에만 설치한다. 외부 사용자 레포는 챗봇
  L3 조건이 충족될 때 연다.
  - 반응형: issue·PR에서 `@rapi`로 부르면 작업한다.
  - 능동형: 레포 주간 리포트를 쓴다.

### C. AI 게이트웨이: LiteLLM 브릿지

- **지금**: 라피 내부의 모델 호출(요약, 재작성, Q&A)을 LiteLLM 뒤로 옮겨 비용을
  한곳에서 집계한다. 로드맵의 "비용 대시보드"가 여기서 해결된다.
- **보류**: 외부 사용자에게 가상 키를 발급하는 일. 근거는 인터뷰의 "Claude는 비용
  때문에 안 쓴다" 한 건뿐이다. 두 번째 사용자 요청이 생기면 연다.
- **원칙**: 구독 로그인 기반 CLI(codex, claude 등)로 남의 요청을 실행하지 않는다.
  provider 이용약관의 계정 공유 금지에 걸릴 가능성이 크다.
  - **현재 예외**: public-agent가 이 방식으로 공개 질문에 답한다. 처리는 "public-agent
    전환" 절을 따른다.
- **과금**: 하지 않는다. 사용량 계량과 예산 한도는 처음부터 둔다.
- **월 비용 상한** `(제안)`: 라피 전체 모델 비용에 월 상한을 둔다.
  - 80%에 이르면 운영자에게 알린다.
  - 100%가 되면 공개 기능(Q&A, 재작성)을 멈춘다. 운영자 기능은 유지한다.
- **하네스 연결 확인**: Codex CLI를 게이트웨이에 연결할 수 있는지는 하네스를
  게이트웨이로 옮길 때 확인한다. public-agent 전환과 요약·Q&A는 직접 호출이라
  이 확인이 필요 없다("모델 실행 방식").
  - Codex 설정의 `model_providers`에 `base_url`과 `env_key`를 둘 수 있고,
    `wire_api`는 `responses`만 지원하는 것으로 리뷰에서 확인됐다. 구현 전에 사용
    중인 Codex 버전의 문서로 다시 확인한다.
  - 따라서 LiteLLM이 해당 모델에 Responses API를 제공해야 한다.
  - public-agent는 `--ignore-user-config`와 `CODEX_HOME`을 쓰므로 설정 위치도
    맞춰야 한다.

### D. 웹: 구독 설정 + 아카이브

- **1단계 최소판**
  - 로그인: **Discord OAuth 하나**로 시작한다. 학습자는 Discord를 수시로 본다.
  - 내 구독: 트랙, 빈도, 받을 채널
  - 아카이브(블로그)
- **나중**
  - 메일 매직 링크: 0단계 결과로 메일 채널을 쓰기로 했을 때만
  - GitHub OAuth: GitHub App을 외부에 열 때
  - 운영자 대시보드: 지금은 기존 브리핑 페이지와 `/상태`로 충분하다. 운영 화면이
    실제로 부족해질 때 만든다.
- 기존 서명 링크 경로(`/b/<uuid>`)는 계정 모델이 생기면 그 안으로 흡수한다.

## 모델 실행 방식

하네스를 하나로 고르지 않고, 일의 종류에 따라 나눈다. 지금은 요약
(`packages/adapters/src/summarizer.ts:157`), ChatOps(`apps/chat/src/executor.ts:50`),
public-agent 모두 Codex CLI를 자식 프로세스로 띄운다.

| 일 | 실행 방식 | 이유 |
|---|---|---|
| 요약, 재작성, 분류, 아카이브 Q&A, 챗봇 L1·L2 | **하네스 없이 LiteLLM 직접 호출**, 필요한 도구만 직접 정의 | 파일 수정·쉘이 필요 없다. 프로세스 기동과 에이전트 프롬프트 비용이 없다. 구독 로그인 문제가 구조적으로 사라진다. JSON 스키마 출력을 그대로 쓴다. |
| 운영자 ChatOps, 운영자 레포 GitHub App | **코딩 하네스 CLI**. Codex를 유지하고 senpi를 두 번째 어댑터로 시험한다. | 취소·재시작·비밀값 격리가 Codex 기준으로 검증돼 있다. senpi는 OpenAI 호환 provider로 LiteLLM에 바로 붙고 다중 공급자를 지원한다. |
| public-agent, 챗봇 L3(남의 요청) | Codex의 read-only sandbox, 또는 컨테이너 샌드박스 안의 하네스 | senpi는 샌드박스가 없다("권한은 확인 정책이지 샌드박스가 아니다"). 컨테이너 샌드박스가 생기기 전까지 senpi를 쓰지 않는다. |

- 직접 에이전트 루프를 만들지 않는다.
- 실행 엔진은 하네스를 어댑터로 분리한다. OMP의 `apps/omp/src/providers.ts` 패턴을
  엔진으로 옮긴다.
- 운영자 본인 작업은 구독 로그인을 써도 된다. 남의 요청은 API 키(게이트웨이)로만
  실행한다.
- 하네스 쪽 게이트웨이 연결은 하네스를 옮길 때만 필요하다. 0단계의 Codex→LiteLLM
  확인은 시급도가 낮아진다.

### senpi 사용 조건

- senpi(`code-yeongyu/senpi`, MIT)는 pi-mono 기반 코딩 에이전트다. README가 스스로
  "실험적, 프로덕션 파이프라인을 걸지 말 것"이라고 적고 있다.
- 사용 조건
  - 버전을 고정한다. 바꾸는 절차는 "하네스 버전 갱신"을 따른다.
  - 텔레메트리와 업데이트 확인을 끈다(`PI_TELEMETRY=0`, `enableInstallTelemetry:
    false`, 업데이트 확인 비활성).
  - 프로젝트 신뢰를 `defaultProjectTrust: "never"`로 고정한다. 레포 안의 `.pi/`
    설정과 확장이 실행되지 않게 한다.
  - 운영자 작업 몇 건을 Codex와 나란히 돌려 품질·시간·토큰을 비교한 뒤 기본값으로
    쓸지 정한다.
- 안정성이 더 필요하면 상위 pi-mono를 대안으로 둔다.

### 하네스 버전 갱신

하네스(senpi, Codex) 버전은 라피가 판단하고, 운영자가 버튼으로 반영한다.

1. **감지**: worker가 고정된 하네스의 GitHub 릴리스를 확인한다. 기존 GitHub 수집을
   쓴다.
2. **평가**: 새 버전을 운영 경로와 분리된 디렉터리에 설치해 검사한다.
   - 릴리스 노트에서 호환성을 깨는 변경, 보안 수정, 설정 이름 변경을 요약한다.
   - 고정된 점검 작업 몇 개를 현재 버전과 새 버전으로 각각 돌려 성공 여부, 시간,
     토큰을 비교한다.
   - 텔레메트리 끄기, 프로젝트 신뢰 `never`, 비밀값 격리가 그대로 지켜지는지
     확인한다.
   - 결과를 "반영 추천" 또는 "보류 추천"과 근거로 정리한다.
3. **알림**: 운영자에게 Discord DM으로 보낸다. 버튼은 `[반영]`, `[건너뛰기]`,
   `[나중에]`다.
   - 보류 추천이어도 운영자가 반영을 고를 수 있다.
   - 버튼은 운영자(SUPERADMIN)만 누를 수 있다.
4. **반영**: `[반영]`을 누르면 고정 버전을 바꾸는 PR을 만든다. CI가 통과하면
   머지되고, 기존 자동 배포가 VM에 반영한다.
   - 반영 결과를 같은 DM에 알리고 `[되돌리기]` 버튼을 붙인다.
   - 되돌리기도 같은 PR 경로로 이전 버전을 복원한다.
5. **기록**: 감지, 평가, 결정, 반영, 되돌리기를 모두 실행 기록으로 남긴다.

자동으로 버전을 올리지 않는다. 평가가 통과해도 운영자 버튼 없이 반영하지 않는다.

## public-agent 전환

C의 원칙과 현재 public-agent 동작이 충돌한다. 다음 순서로 푼다 `(제안)`.

1. **0단계 동안**: 기존 공개 커뮤니티 범위에서만 지금처럼 유지한다. 이 기간은
   위험을 감수하는 것으로 기록한다. 새 사용자에게 Q&A를 홍보하지 않는다.
2. **1단계 시작 전**: public-agent를 API 키 또는 게이트웨이 경유로 바꾼다.
   - 이때 웹 검색은 끈다.
   - 아카이브 Q&A가 준비되기 전까지 공개 질문은 "아카이브에 있는 글 링크 안내"로
     답한다.
3. 전환이 끝나지 않으면 1단계(공개 구독 확대)를 시작하지 않는다.

격리 경계(`rapi-public` 사용자, Unix 소켓, `--ephemeral`, read-only sandbox)는
그대로 유지한다.

## 기둥을 잇는 기능

### 우선

1. **아카이브 Q&A**
   - 뉴스레터·블로그 글을 근거로 답하고 출처 링크를 붙인다.
   - 아카이브에 근거가 없으면 모른다고 답하고 가까운 글을 안내한다.
   - public-agent 전환 직후, 실행 순서 2단계에서 만든다.
2. **반응 기반 선별의 구독자 확장**
   - 운영자 전용인 👍/👎 반응과 학습 순위(`preference.ts`)를 구독자별로 넓힌다.
   - 트랙 안 항목 선별에 반영한다.

### 보류

- **학습자 실습 루프**(과제 제출 → 리뷰): 챗봇 L3, 샌드박스, GitHub App 외부 공개,
  게이트웨이 키가 모두 전제다. 그 조건이 충족된 뒤 다시 검토한다.
- **릴리스 노트·체인지로그 자동 작성**: 개발자 트랙과 함께 보류
- **뉴스레터 항목별 Discord 토론 스레드**: 구독자가 생긴 뒤 검토

### 하지 않음

- 일정·기억 같은 개인 비서 기능 확장. 기존 기능은 동결한다.
- 모델 비교 플레이그라운드, 공개 상태 페이지
- 기둥 하나를 위한 별도 저장소. LiteLLM은 외부 제품을 배포하는 것이라 예외다.

## 챗봇

챗봇은 범용 대화가 아니라 기둥으로 들어가는 대화형 입구다. 웹과 Discord가 같은
백엔드를 쓰고, 모든 모델 호출은 게이트웨이를 거친다.

- **근거 있는 답**: 아카이브를 근거로 답하고 출처 링크를 붙인다. 근거가 없으면
  모른다고 답한다.
- **기둥 기능을 대화로 쓰기**: "이번 주 학습자 트랙 뭐 나와?", "빈도 주 1회로
  바꿔줘"처럼 묻는다.
- **스레드 단위 맥락**: 같은 Discord 스레드나 웹 대화 안에서만 앞 대화를 이어
  받는다.
  - 맥락은 대화가 끝나면 지운다. 보관 기간은 최대 24시간이다 `(제안)`.
  - 장기 저장하지 않으므로 "원문·세션 비저장" 원칙과 같은 범위에 둔다.

### 공개 사용자에게 여는 범위 (L1–L4)

| 단계 | 범위 | 여는 조건 |
|---|---|---|
| L1. 읽기 도구 | 아카이브 검색, 트랙 미리보기, 내 구독 설정 | 아카이브 Q&A 완성 |
| L2. 설명·조언 | 에러 설명, 공개 레포 구조 설명. 코드는 실행하지 않는다. | L1 이후, 프롬프트 인젝션 대책 확정 |
| L3. 내 레포 작업 | 사용자 본인 레포에서 실행하고 결과는 PR로만 낸다. | 샌드박스 결정, 외부 게이트웨이 키, GitHub App 외부 공개 |
| L4. 서버 운영·배포 | 공개 사용자에게 열지 않는다. | 소유자 전용 |

- **L2의 위험**: 레포를 읽는 순간 README, issue, PR 본문이 프롬프트 인젝션 통로가
  된다. 레포 내용을 읽은 응답에서는 도구 호출을 막는다.
- **L3의 조건**

  | | 소유자 ChatOps | 공개 사용자 |
  |---|---|---|
  | 대상 | 운영 VM, 라피 레포 | GitHub App을 설치한 사용자 본인 레포만 |
  | 실행 위치 | VM에서 바로 | 작업마다 일회용 샌드박스 |
  | 모델 비용 | 운영자 계정 | 사용자별 게이트웨이 가상 키와 예산 |
  | 결과물 | 직접 수정·배포 | PR만 |
  | 비밀값 | VM 환경 | 해당 레포 전용 단기 토큰만 |

  - **PR만 내도록 강제하는 방법**: GitHub App 설치 토큰에 `contents:write`가
    있으면 보호되지 않은 main에도 push할 수 있다. fork에 push하고 PR을 여는
    방식으로 강제한다.
  - **샌드박스는 L3의 선결 조건이다.** 단일 VM 원칙(D-007)과 충돌하고 비용이 든다.
  - 동시 실행 수, 작업당 시간, 하루 작업 수에 한도를 둔다.

### 하지 않음

- **잡담·범용 비서**: 차별점이 없고, 비용이 들고, 축을 다시 흐린다.
- **공개 사용자의 장기 대화 기억**: 개인정보 처리 범위가 커지고, public-agent의
  격리 경계와 충돌한다. 개인화는 사용자가 직접 설정한 값(트랙, 빈도, 관심
  키워드)으로만 한다.
- **웹 검색**: 비용이 사용자 수에 비례해 늘고, 프롬프트 인젝션 경로가 되며, 근거
  품질이 고르지 않다. public-agent 전환 때 끈다.

## 채널별 역할

Discord에서 모든 것을 하지 않는다.

| 채널 | 맡는 일 |
|---|---|
| 웹 | 구독 설정(트랙·빈도·채널), 아카이브, 나중에 Q&A |
| Discord | 학습자 트랙 DM 발송, `라피야!` 대화와 작업 지시, 커뮤니티, 즉시 알림 |
| 메일 | 0단계 결과로 쓰기로 했을 때만. 뉴스레터, 구독 확인, 수신거부 |
| GitHub | 운영자 레포의 `@rapi` 호출과 주간 리포트 |

- Discord 봇 DM은 받는 사람이 봇과 같은 서버에 있어야 보낼 수 있다. 구독은
  커뮤니티 서버 가입과 옵트인을 거친다.

### slash 명령 정리 (18개)

| 처리 | 명령 | 수 |
|---|---|---|
| Discord에 남김 | `/브리핑`, `/검색`(결과에 웹 링크), `/데이터삭제`, `/취소`, `/대화채널`, `/대화해제` | 6 |
| 동결(그대로 둠) | `/일정` | 1 |
| 웹으로 이동 | `/구독`, `/구독해제`, `/수집원`, `/발송내역`, `/상태`, `/사용량`, `/사용정책`, `/서버구성`, `/웹훅` | 9 |
| 제거 | `/작업`, `/승인` | 2 |

- `/브리핑`은 USER 공개 명령이다. 웹으로 옮기면 Discord만 쓰는 사용자가 잃으므로
  남긴다.
- `/데이터삭제`는 Discord만 쓰는 사용자의 삭제 경로다. 웹에 같은 기능을 만들어도
  Discord 경로를 남긴다(`docs/data-lifecycle.md`의 절차가 slash 기준이다).
- `/구독`·`/구독해제`는 웹이 생기기 전까지 Discord에 남긴다.
- README는 명령을 17개로 적고 있다. 실제 정의는 18개다(`apps/bot/src/discord-http.ts`).

## 실행 순서

### 0단계: 검증 (코드 거의 없음)

- **실험**: 기존 `free-tokens` 피드와 도구 입문 글을 학습자 5명 이상에게 보낸다.
  - 인터뷰 대상자는 셈에서 뺀다.
  - 반드시 옵트인을 받는다.
  - 받는 방식은 Discord DM이나 큐레이션 채널 초대 중에서 받는 사람이 고른다.
  - 빈도도 받는 사람이 고른다.
  - 3주 동안 진행한다.
- **측정**: Discord DM은 열람을 잴 수 없다. 추적 링크 클릭, 자발적 답장·공유,
  옵트아웃을 잰다.
- **기준** `(제안)`

  | 판정 | 조건 | 결과 |
  |---|---|---|
  | 성공 | 추적 링크를 주 1회 이상 클릭한 사람이 30% 이상, 자발적 답장·공유 2건 이상, 옵트아웃 1명 이하 | 1단계 진행 |
  | 중단 | 클릭률 10% 미만, 또는 옵트아웃 2명 이상 | 학습자 트랙을 다시 설계한다. 1단계는 시작하지 않는다. |
  | 분기 | "메일로도 받겠다"는 사람이 과반 미만 | 1단계에서 메일(발송 서비스, SPF·DKIM·DMARC)을 뺀다. |

- **추가 인터뷰**: 돈을 낼 의향, 적당한 빈도, "쓸 만하다"의 기준을 묻는다. 개발자
  1명 이상도 인터뷰한다.
- **기술 확인**: senpi를 운영자 작업에 시험한다("senpi 사용 조건"). Codex
  CLI→LiteLLM(Responses API) 연결은 하네스를 게이트웨이로 옮길 때 확인한다.
- **결정**: public-agent 전환 방식과 1단계 전 결정 사항(아래)을 확정한다.
- **완료 조건**: 기준표의 판정이 나왔고, 기술 확인 결과가 기록됐다.

### 1단계: 학습자 구독 최소판

- 진입 조건: 0단계 성공, public-agent 전환 완료
- 구성
  - 웹 구독 페이지(Discord OAuth, 트랙·빈도·채널 선택)
  - 학습자 트랙 Discord DM 발송, 수신거부
  - 메일 발송은 0단계 분기 결과에 따른다.
  - 블로그 아카이브 자동 게시(운영자 승인 후)
- 완료 조건: 외부 구독자가 웹에서 구독하고, 고른 빈도와 채널로 학습자 트랙을
  받고, 웹에서 지난 호를 읽고, 수신거부할 수 있다.
- 성공 지표 `(제안)`: 1단계 공개 후 8주 동안 다음을 본다.
  - 주간 활성 구독자(클릭 1회 이상) 비율 40% 이상
  - 월 옵트아웃률 10% 이하
  - 미달하면 트랙 구성과 빈도를 다시 설계한다.

### 2단계: 아카이브 Q&A

- 아카이브 Q&A를 만들고 챗봇 L1을 연다.
- 완료 조건: 공개 질문이 아카이브 근거와 출처 링크로 답해지고, 근거가 없으면
  모른다고 답한다.

### B·C (독자와 무관, 0단계부터 병행 가능)

- **B**
  - OMP를 제거한다(B 절의 범위).
  - ChatOps를 실행 엔진으로 정리한다.
  - 하네스를 어댑터로 분리하고 senpi 어댑터를 붙인다.
  - 하네스 버전 갱신(감지 → 평가 → 버튼 반영 → 되돌리기)을 만든다.
  - 운영자 레포에 GitHub App을 붙인다.
  - 완료 조건: Discord와 GitHub 어느 쪽에서 요청해도 같은 엔진·같은 기록으로
    실행된다. MVP 매니페스트가 새 조건으로 통과한다.
- **C**
  - LiteLLM을 배포하고 라피 내부 호출을 옮긴다.
  - 월 비용 상한과 초과 시 동작을 구현한다.
  - 완료 조건: 기능별 모델 비용이 집계되고, 상한에 이르면 정해진 동작을 한다.

### 그 이후 (조건부)

- 챗봇 L2: 인젝션 대책을 확정한 뒤
- 외부 게이트웨이 키: 두 번째 사용자 요청이 생긴 뒤
- 챗봇 L3, 학습자 실습 루프: 샌드박스 결정 이후
- 개발자 트랙: 개발자 인터뷰 근거가 생긴 뒤

## 1단계 전에 정해야 할 것

1. public-agent 전환 방식(API 키 또는 게이트웨이)과 시점
2. 0단계 성공·중단 기준의 숫자 확정
3. 메일 채널을 쓸지(0단계 분기 결과로 결정)
4. 웹 스택: 정적 블로그 빌드(`scripts/build-blog.mjs`)를 확장할지, 별도 웹 앱을
   둘지. 1단계 전체가 이 결정에 달려 있다.
5. 큐레이션 피드 5종과 학습자 트랙의 관계 확정(A 절의 표)
6. Discord만 쓰는 USER의 `/브리핑`·`/데이터삭제` 경로 유지 확인
7. 직접 호출로 옮길 작업 범위(요약, 재작성, public-agent 답변)와 호출 라이브러리
8. 월 모델 비용 상한과 초과 시 동작
9. 초기 품질 게이트(운영자 승인 발송) 적용 여부

## 기존 결정과의 충돌

이 방향은 사실상 **다중 사용자 서비스로의 전환**이다. 승인되면 다음을 고친다.

- **D-001** "Discord가 기본 사용자 인터페이스다": 웹이 구독 설정과 아카이브를
  맡고, Discord는 발송·대화·커뮤니티 채널이 된다.
- **D-004** MDX 블로그: 유지하되 역할을 "뉴스레터 아카이브"로 넓힌다.
- **D-005** "개발 구현은 OMP에 위임한다": 폐기한다. 이미 D-008(ChatOps 직접
  실행)이 사실상 대체했고, OMP 제거로 끝난다. 로드맵 Phase 5 완료 조건에 남은
  D-005 문구도 고친다.
- **D-006** 이메일 뉴스레터: 동일 batch 원칙은 트랙별 batch로 바뀐다. 메일 자체가
  0단계 결과에 따라 선택 사항이 된다.
- **D-007** 단일 VM 모듈러 모놀리스: 1·2단계는 유지한다. 챗봇 L3의 샌드박스가
  이 원칙과 충돌하므로 L3 결정 때 다시 다룬다.
- **D-009** 기본 모델: 네 곳의 값이 다르다. 게이트웨이 도입 때 하나의 기준으로
  정리한다.

  | 위치 | 값 |
  |---|---|
  | D-009 결정문 | `gpt-5.3-codex-spark` |
  | 계약 기본값 `packages/contracts/src/models.ts:3` | `gpt-5.6-sol` |
  | DB 기본값 `packages/db/src/chatops-store.ts:58` 등 | `gpt-5.3-codex-spark` |
  | public-agent `apps/public-agent/src/executor.ts:5` | `gpt-5.6-luna` |

- **D-010** OMP 다중 공급자 CLI 실행: 폐기한다.
- **O-004** 이메일 전송 방식: 0단계 분기 결과에 따라 결정하거나 닫는다.
- **O-005** 모델 공급자와 라우팅: 게이트웨이(C)로 해결한다.
- **PRD §6** "다중 사용자 SaaS와 결제 제외", **로드맵** "미루는 것: 다중 사용자와
  결제": 다중 사용자는 포함으로 바꾼다. 결제는 계속 제외한다.

## 위험과 제약

- **공개 ingress**
  - 지금 gateway는 POST 3개 경로, `/blog/`, 서명 링크 경로(GET `/b/<uuid>`와
    반응 POST 4종)를 연다. 서명 링크의 인증은 HMAC 토큰뿐이다.
  - 웹 로그인과 구독 설정이 추가되면 경로별 인증과 속도 제한을 처음부터 둔다.
- **프롬프트 인젝션**
  - 수집한 글, 레포 내용, 웹 페이지가 모델에 들어간다.
  - 외부 내용을 읽은 응답에서는 도구 호출을 막는다.
- **법무 확인 항목**
  - 정보통신망법 §50: 무료 도구·프로모션 모음이 영리 목적 광고성 정보로 해석될 수
    있다. 사전 동의와 표기 의무를 확인한다.
  - 개인정보처리방침: Discord 계정, 구독 설정, 반응 기록, (메일을 쓰면) 메일
    주소를 추가한다. [데이터 보관·삭제 운영](data-lifecycle.md) 범위를 넓힌다.
  - Discord 개발자 정책: 요청하지 않은 DM을 제한한다. 옵트인을 받은 사람에게만
    보낸다.
  - provider API 약관: 외부 가상 키를 발급하기 전에, 제3자에게 모델 접근을 제공하는
    것이 허용되는지와 사용 정책 책임이 누구에게 있는지 확인한다.
  - 저작권: 요약과 원문 링크 원칙(PRD §3.2) 안에서만 재작성한다.
- **비용**: 재작성, Q&A, (나중에) 무료 크레딧과 샌드박스가 모두 운영자 부담이다.
  과금이 없으므로 월 상한이 유일한 차단 장치다.
- **메일 평판**: 메일을 쓰기로 하면 구독 확인, 수신거부, 발송 도메인 인증
  (SPF·DKIM·DMARC)을 처음부터 넣는다.
- **운영 부담**: 지금도 상시 서비스 10개(README는 9개로 적음)와 타이머 6개를 혼자
  운영한다. LiteLLM, 웹 앱, GitHub App 웹훅을 추가할 때마다 알림·백업·복구 범위에
  넣는다.

## 열린 질문

1. 발송 서비스: 메일을 쓰기로 하면 Resend, SES 등 중 무엇을 쓸 것인가
2. 샌드박스: L3를 열 때 VM에서 직접 돌릴 것인가, 호스팅 서비스를 쓸 것인가
3. 외부 게이트웨이 키: 연다면 누구에게, 얼마의 무료 예산으로 줄 것인가
4. 기억·일정을 동결로 둘지 제거할지
5. 크롤러 운영 방식(보류 중)
6. `rapi-web-proxy.service`를 VM에서 내릴 것인가
